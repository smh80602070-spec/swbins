# VERTICAL_SLICE

master.md 3.1절·35장(01~35단계)의 Vertical Slice 설계. **어느 게임부터 만드는가**를
먼저 정한다 — master.md 39장이 "SAGA Core → Vertical Slice → GO → DUNGEON → FOREST
→ STORY → REALM" 순서를 이미 못박아 뒀으므로, 첫 Vertical Slice는 **사가만리(GO)**
기준이다.

GO를 고른 다른 이유: LEGACY_FEATURE_AUDIT.md 2장에서 본 대로 GO의 웹판(saga-go)은
이미 `land.js`(손으로 그린 1008m 지역) · `npc.js`(주민 10명, 시각의 순수함수) ·
`animal.js`(짐승 5종) · `event.js`(사건 11종) · `duel.js`+`battle3d.js`(전투)가
전부 실제로 돌고 있다 — **베낄 실체가 있는 유일한 판**이다. DUNGEON은 시스템이
가장 많고, STORY는 플랫폼 물리가 걸리고, REALM은 턴제라 애초에 실시간 루프가 없다.
GO가 가장 적은 리스크로 "Godot에서 실제로 재미있는 루프 하나"를 검증할 수 있다.

**중요 — 몬스터가 아니라 사람이다.** master.md 26~35절 원문은 "적"·"보스"라는
말을 쓰지만, LEGACY_FEATURE_AUDIT.md 0장에서 확인했듯 이 프로젝트에 몬스터는
없다. GO의 "적"은 사건 속에서 만나는 **도적·정찰병 같은 사람과, 늑대 무리** 뿐이고
그마저 싸우지 않고 피하거나 값을 치를 수도 있다. 아래 26~35 항목은 master.md의
번호를 그대로 따르되 내용은 GO의 실제 정체성에 맞춰 다시 썼다.

## 26. Vertical Slice 범위 확정

포함:

```text
플레이어 이동(3인칭, 모바일 가상 조이스틱)
카메라(추적 + 줌 + 회전)
테스트 지역 하나(웹판의 "하북의 작은 마을" 1008m 축소판)
주민 1~2명(대화만, 등용 대상 아님)
사건 1종(도적의 습격 — 전투로 이어지는 유일한 사건)
전투(속공·필살·회피, duel.js 규칙을 GDScript로 재구현)
사건에서 만나는 상대를 물리치면 그 인물이 등용된다
부대(1~2명) 성장(레벨 개념 정도)
저장/로드(로컬 파일 하나)
```

제외(다음 슬라이스로 미룸):

```text
소문 시스템 · 사진 모드 · 발견 도감 5갈래 · 계절 · 날씨
짐승 생태(사슴·늑대·까치 등 관찰용 동물)
역참/성채 같은 건물 POI
후처리(블룸/톤매핑) 등 그래픽 마감
```

이유: master.md 3.1절 "Vertical Slice가 재미있지 않으면 콘텐츠를 늘리지 않는다".
GO의 정체성 중 "걷는다 → 만난다 → 등용한다" 세 동사만 검증하면 충분하고, 나머지는
그 루프가 재미있다고 확인된 뒤에나 의미가 있다.

## 27. 첫 번째 테스트 지역 설계

웹판 `js/land.js`의 지역을 그대로 참고해 축소한다(새로 상상하지 않는다 —
이미 검증된 배치를 재사용).

```
길이 이어진다: 북쪽 굴 입구 → 마을 → 남쪽 다리 → 폐허
크기: 원점(마을 중심) 둘레 300m 사방 정도로 축소해 시작(웹판은 1008m —
       처음엔 그 1/3 규모, Vertical Slice 승인 뒤 2026-09-11에 528m
       사방(11×11칸)으로 한 차례 넓혔다 — games/saga_go/data/test_map.gd
       참고. 마을·사건 배치는 그대로 두고 사방에 테를 둘렀을 뿐이라
       기존 검증은 안 깨졌다)
지형: 마을(집 몇 채) · 길 · 다리 · 논밭 약간 · 숲 가장자리(논밭·숲은
       2026-09-11 확장 때 처음 실제로 채웠다 — 그 전엔 이 문서에만
       있고 지도엔 없었다)
```

Godot 구현은 GridMap 또는 손으로 배치한 Node3D 씬 하나(`TestVillage.tscn`)로
시작한다 — 웹판처럼 글자 지도(ASCII map)로 정의하고 스크립트가 그 위에 지형/
오브젝트를 얹는 방식을 그대로 가져오면(데이터 기반 설계, master.md 7장과 합치)
나중에 지역을 늘릴 때도 같은 패턴을 반복할 수 있다.

## 28. 플레이어 목표 정의

**"마을에서 시작해 걸어서 도적을 만나고, 물리치고, 그 도적을 부대로 들인다."**

한 문장짜리 목표를 넘는 콘텐츠는 이번 슬라이스에 넣지 않는다.

## 29. 첫 번째 적 설계

GO에는 몬스터가 없으므로 "적"은 **사건 속 인물**이다. 웹판 `event.js`의
"도적의 습격" 사건을 그대로 가져온다.

```
이름: 도적(盜賊)
전투력: 120 (웹판 event.js와 동일 — 임의로 새 수치를 만들지 않는다)
등장: 길/들/논밭/폐허, 밤에 잦다 (Vertical Slice에서는 시간대 단순화 —
      낮/밤 둘 중 하나만 먼저 구현하고 낮으로 고정해도 됨)
선택지: 맞선다 / 값을 치른다 / 달아난다 (셋 다 구현 — "맞선다"만 전투로 감)
승패: 이길 가망은 부대 전투력과 견주되 0.12~0.88로 눌러 둔다(웹판 규칙 그대로 —
      확실해지면 고를 뜻이 사라진다는 원칙도 같이 가져온다)
```

## 30. 첫 번째 보스 설계

Vertical Slice 단계에서는 **보스를 따로 만들지 않는다.** master.md 원문은
보스 1종을 요구하지만, GO의 실제 정체성(사건 기반 조우)에는 "보스"라는 개념이
없다 — 도적 두목 같은 강화형 사건은 다음 슬라이스(콘텐츠 확장 단계)에서
"도적" 사건의 변형으로 추가한다. 지금 억지로 만들면 master.md 2장의 절대
금지("기능만 많고 재미없는 게임 제작")를 어기게 된다.

## 31. 첫 번째 퀘스트 설계

퀘스트도 따로 만들지 않는다. GO의 "사건"(event) 자체가 이미 목표-보상 구조를
갖고 있으므로(도적 습격 → 맞선다 → 승리 → 등용), 이번 슬라이스에서는 **사건이
곧 퀘스트**다. 별도 퀘스트 로그 UI는 이후 슬라이스에서 "마을의 부탁"·"사라진
아이" 같은 다른 사건 유형을 추가할 때 같이 만든다.

## 32. 첫 번째 던전 설계

GO에는 던전이 없다(그건 DUNGEON의 몫). "폐허"·"굴 입구" 같은 POI를 지형에
배치는 하되(27절), Vertical Slice에서는 입장 가능한 별도 씬으로 만들지 않는다
— 지도 위의 눈에 보이는 랜드마크로만 존재한다.

## 33. 첫 번째 장비 설계

Vertical Slice에서는 장비를 구현하지 않는다. 부대 전투력(`partyPower` 개념,
웹판 `hero.js` 참고)이 인물 레벨만으로 정해지는 것으로 충분하다 — 장비는
DUNGEON에서 이미 훨씬 무거운 시스템(등급+접사+소켓)으로 설계돼 있으므로
(LEGACY_FEATURE_AUDIT.md 참고), saga_core에 장비 인터페이스를 놓을 때 DUNGEON
설계를 먼저 보고 얇게 잡는 게 맞다 — GO Vertical Slice가 먼저 자기 방식대로
확정하면 나중에 뒤집어야 한다.

## 34. 첫 번째 스킬 설계

웹판 `duel.js`를 그대로 재구현한다 — 새로 설계하지 않는다.

```
기본 공격(속공)
필살(쿨다운 있음, 큰 피해)
회피
```

적 AI는 "강타 예고" 패턴 하나만(웹판 duel.js 그대로) — 공격 전에 짧은 예고를
보여주고 플레이어가 회피할 시간을 준다.

## 35. 첫 번째 보상 루프 설계

```
도적을 물리친다
  ↓
도적이 부대에 합류한다(등용 — GO의 핵심 재화는 "사람"이다, 장비나 골드가 아니다)
  ↓
부대 전투력이 오른다
  ↓
다음 사건(같은 도적 사건이 재등장, 이번엔 부대가 강해져 이길 가망이 더 크다)
```

master.md 17장의 "탐험→발견→전투→보상→성장→다시 탐험" 루프를, GO의 실제 재화인
"인물 등용"으로 바꿔 낀 것이다. 골드나 장비 드랍으로 루프를 채우지 않는다 —
이 판의 정체성은 처음부터 "사람을 모은다"였다.

## 완료 조건 (master.md 36장 대응)

다음이 되면 이 Vertical Slice는 성공이다:

```
게임 실행 → 3D 마을에 들어간다 → 걷는다 → 주민과 대화한다
→ 걷다가 "도적의 습격" 사건을 만난다 → 맞선다를 고른다
→ 실시간 전투(공격/필살/회피) → 도적을 이긴다 → 도적이 부대에 합류한다
→ 부대 전투력이 올랐다는 걸 화면에서 확인한다 → 저장한다 → 다시 켜서 이어진다
```

이 열두 단계가 실제로 손에 잡히게 재미있는지가 master.md 37장의 평가 기준이다.
재미가 없으면(38장) 콘텐츠를 더 넣지 않고 이동감·카메라·전투 타격감부터
고친다 — 다음 세션이 실제 Godot 씬을 만들기 시작하면 이 문서의 완료 조건으로
스스로 검증한다.

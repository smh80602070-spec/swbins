# VERTICAL_SLICE

PLAN.md 3장의 Vertical Slice 설계. **범위는 `saga-godot/docs/
VERTICAL_SLICE.md`와 똑같다** — 게임 디자인(어떤 사건, 어떤 전투 규칙,
어떤 완료 조건)은 엔진과 무관해서 다시 고민하지 않는다(PLAN.md 0·4장
"기획은 공유, 구현은 별개"). 이 문서는 그 결정을 **Unity 구현 언어로
옮겨 적는 것**만 한다 — 새 디자인 결정은 안 한다.

## 왜 GO인가 (saga-godot 문서 그대로)

`saga-godot/docs/VERTICAL_SLICE.md` 3~19행 참고 — 요약: 웹판 saga-go가
`land.js`(1008m 지역)·`npc.js`(주민 10명)·`animal.js`(짐승 5종)·
`event.js`(사건 11종)·`duel.js`(전투)가 전부 실제로 돌고 있어 "베낄
실체가 있는 유일한 판"이다. DUNGEON은 시스템이 많고, STORY는 플랫폼
물리, REALM은 턴제라 실시간 루프가 없다. **몬스터가 아니라 사람이다**
— GO의 "적"은 사건 속 도적·정찰병 같은 사람이고, 싸우지 않고 피하거나
값을 치를 수도 있다.

## 범위 확정 (saga-godot 26절과 동일)

포함:

```text
플레이어 이동(3인칭, 모바일 가상 조이스틱)
카메라(추적 + 줌 + 회전)
테스트 지역 하나(웹판의 "하북의 작은 마을" 1008m 축소판, 300m 규모)
주민 1~2명(대화만, 등용 대상 아님)
사건 1종(도적의 습격 — 전투로 이어지는 유일한 사건)
전투(속공·필살·회피, duel.js 규칙을 C#으로 재구현)
사건에서 만나는 상대를 물리치면 그 인물이 등용된다
부대(1~2명) 성장(레벨 개념 정도)
저장/로드(로컬 파일 하나)
```

제외(다음 슬라이스로 미룸): 소문 시스템·사진 모드·발견 도감 5갈래·
계절·날씨·짐승 생태·역참/성채 POI·후처리 그래픽 마감.

## 테스트 지역 설계 (saga-godot 27절과 동일한 지도)

웹판 `js/land.js`를 그대로 참고해 축소한다. **saga-godot의 7×7 글자
지도(`saga-godot/games/saga_go/data/test_map.gd`)를 그대로 재사용한다**
— 두 트랙이 같은 지도를 쓰면 나중에 "같은 조건에서 어느 쪽이 더
자연스러운가"를 비교할 수 있다(0장의 병행 목적과 맞음).

```
^^^C^^^
^TT=TT^
T..=..T
T.HH.RT
T..=..T
~~~B~~~
^^^=^^^

^ 산   T 숲   ~ 강   = 길   H 마을   F 논밭   . 들
C 굴 입구   S 옛 사당   R 폐허   B 다리
칸당 48m, 7×7칸 = 336m 사방
```

### Unity 구현 방식

- 데이터: `Assets/SagaCore/World/TestMapData.cs` — 문자열 배열로 지도를
  들고 있는 순수 데이터 클래스(또는 ScriptableObject, PLAN.md 7장).
  `saga-godot`의 `test_map.gd`를 그대로 베끼지 않고 **같은 글자·같은
  칸 크기·같은 world_pos 규칙만** C#으로 다시 짠다(PLAN.md 2장 —
  GDScript 기계적 번역 금지, 값만 같게).
- 지형: `TerrainBuilder.cs` — 칸을 읽어 땅을 세운다. **주의 — saga-godot이
  2026-09-11에 겪은 함정**: 칸마다 독립된 평면 메시로 채우면 경계가
  바둑판처럼 갈라져 보인다(그 세션의 해법: 정점 색을 이웃 칸과 섞는
  단일 메시, `terrain_builder.gd` `_build()` 참고). Unity 구현은 처음부터
  **단일 Mesh(Procedural Mesh, `Mesh.SetVertices`/`SetColors`/
  `SetTriangles`)로 이어 붙이거나, Unity Terrain의 텍스처 스플랫맵
  블렌딩**을 쓴다 — 나중에 고치는 게 아니라 처음부터 이 함정을 피한다.
- 땅 높이는 saga-godot과 같은 값을 쓴다: 산 +2.5·강바닥 -1.0·나머지는
  0~0.2 사이(사가마을 웹판 "물은 12cm 낮춘다" 원칙과 같음).

## 플레이어 목표 (동일)

**"마을에서 시작해 걸어서 도적을 만나고, 물리치고, 그 도적을 부대로
들인다."**

## 첫 번째 적 설계 (동일 수치)

```
이름: 도적(盜賊)
전투력: 120 (웹판 event.js와 동일 — 임의로 새 수치를 만들지 않는다)
등장: 길/들/논밭/폐허 (Vertical Slice는 낮으로 고정, 낮/밤 시간대는 다음 슬라이스)
선택지: 맞선다 / 값을 치른다 / 달아난다 (셋 다 구현 — "맞선다"만 전투로 감)
승패: 이길 가망은 부대 전투력과 견주되 0.12~0.88로 눌러 둔다(확실해지면
      고를 뜻이 사라진다는 원칙, 웹판 event.js 그대로)
```

보스·퀘스트·던전·장비는 **의도적으로 제외**(saga-godot 30~33절과 동일한
이유 — GO 정체성에 "보스"·"퀘스트 로그"·"던전 입장"·"장비"라는 개념
자체가 없다. 사건=퀘스트, 랜드마크는 보이기만, 부대 전투력은 레벨만으로).

## 첫 번째 스킬 설계 (동일 — duel.js 그대로 재구현)

```
기본 공격(속공)
필살(쿨다운 있음, 큰 피해)
회피
```

적 AI는 "강타 예고" 패턴 하나만 — 공격 전 짧은 예고, 플레이어가 회피할
시간을 준다.

### Unity 구현 방식

`Assets/SagaCore/Combat/DuelRules.cs` — `saga-godot/games/saga_go/
data/duel_rules.gd`가 이미 웹판 `duel.js`(속공·필살·회피·강타 예고
AI, 상수 안 바꾸고 그대로 옮김)를 검증해 둔 판정 로직을 **같은 상수·
같은 규칙으로 C#에 다시 짠다.** GDScript 문법을 C#으로 기계 번역하지
않는다 — 결과 값(승패·기세 감소량 등)이 같은 입력에서 같은 출력을
내는지로 맞는지 확인한다(PLAN.md 2장).

## 첫 번째 보상 루프 설계 (동일)

```
도적을 물리친다
  ↓
도적이 부대에 합류한다(등용 — GO의 핵심 재화는 "사람"이다)
  ↓
부대 전투력이 오른다
  ↓
다음 사건(같은 도적 사건이 재등장, 부대가 강해져 이길 가망이 더 크다)
```

골드나 장비 드랍으로 루프를 채우지 않는다 — "사람을 모은다"가 이 판의
정체성이다.

## 완료 조건 (saga-godot과 동일 — 나중에 두 트랙을 같은 기준으로 비교)

```
게임 실행 → 3D 마을에 들어간다 → 걷는다 → 주민과 대화한다
→ 걷다가 "도적의 습격" 사건을 만난다 → 맞선다를 고른다
→ 실시간 전투(공격/필살/회피) → 도적을 이긴다 → 도적이 부대에 합류한다
→ 부대 전투력이 올랐다는 걸 화면에서 확인한다 → 저장한다 → 다시 켜서 이어진다
```

이 열두 단계가 실제로 손에 잡히게 재미있는지가 PLAN.md 37장의 평가
기준이다. 재미가 없으면(38장) 콘텐츠를 더 넣지 않고 이동감·카메라·
전투 타격감부터 고친다.

## Unity 구현 순서 (PLAN.md Phase 3~8, 21~78단계와 대응)

다음 세션이 이어갈 때 참고할 순서 — saga-godot이 이미 이 순서로
검증했다(같은 방식이 통했다는 뜻이니 그대로 따른다):

1. Phase 3 — 3D World: `TestVillage.unity` 씬, `TerrainBuilder.cs`
   (위 함정 주의), 초목/바위 산포, 강물 표면, 높낮이 충돌
2. Phase 4 — Player: CharacterController 기반 이동, Cinemachine 카메라,
   모바일 가상 조이스틱(Input System On-Screen Controls)
3. NPC 최소 구현(주민 1~2명, 대화만) — saga-godot이 "대화가 전투보다
   먼저 와야 한다"고 순서를 정정했던 교훈 그대로(완료 조건 문구 순서와
   맞춤)
4. Phase 5 — Combat: `DuelRules.cs` + "도적의 습격" 사건 화면
5. Phase 6 — RPG Systems 최소(전투력 계산에 필요한 만큼만): Stats·EXP·
   Level
6. 등용(부대 합류) 연결
7. Phase 8 — Save/Load
8. 완료 조건 열두 단계 전체 플레이 테스트(에디터, GUI 필요 — 몰아서 한 번)
